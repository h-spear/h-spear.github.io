지난 1년여 동안 회사에서 대시보드를 개발하며 프론트엔드와 백엔드 기능 구현뿐만 아니라 화면 구성과 사용자 경험도 함께 고민해 왔습니다.   
별도의 UX 디자이너가 없는 환경이었기 때문에, 고객의 요구사항을 실제 화면으로 구체화하는 과정도 담당했습니다.   

백엔드 개발을 중심으로 공부해 온 저에게 UI 설계와 디자인은 상대적으로 익숙하지 않은 영역이었습니다.   
그럼에도 고객과 요구사항에 대한 이해를 맞추고 피드백을 효과적으로 주고받기 위해 여러 방법을 시도했습니다.   

처음에는 동작하는 UI 시안을 코드로 직접 구현했습니다. 이후 이 방식의 한계를 경험하면서 AI 기반 디자인 도구를 도입하고, 팀이 함께 사용할 수 있는 공통 UI 기준을 구축하는 방향으로 프로세스를 발전시켰습니다.   

이 글에서는 담당했던 프로젝트와 서비스의 구체적인 내용은 제외하고, **고객과 UI 피드백을 효과적으로 주고받는 방법에 대한 고민에서 출발해 프론트엔드 UI 개발 프로세스를 개선해 온 경험을 정리합니다.**

## **별도 디자인 시안 대신 코드 기반 데모를 선택한 이유**

---

### **1. 동작하는 화면을 통한 요구사항 구체화**
고객의 요구사항은 주로 PPT나 간단한 예시 이미지로 전달받았습니다. 하지만 이러한 정적 자료만으로는 사용 흐름과 화면의 상태 변화를 파악하기 어려웠습니다.   
특히 제가 담당한 대시보드는 여러 도구에 분산된 데이터를 하나의 화면에 통합해야 했습니다. 어떤 데이터를 어떻게 보여줄지뿐만 아니라, 사용자가 기능을 이용하는 흐름도 구체화해야 했습니다.   
이를 위해 개발 초기부터 고객이 직접 조작할 수 있는 화면을 만들었고, 고객과 같은 화면을 보며 기능의 흐름을 확인하고 세부 요구사항을 정리했습니다.   

### **2. 별도 디자인 시안 제작의 부담**
별도의 디자이너 없이 UI 설계와 프론트엔드 개발을 함께 담당하는 상황에서, Figma로 시안을 만든 뒤 같은 화면을 다시 코드로 구현하면 추가 공수가 발생한다고 판단했습니다.   
반면 프론트엔드 기술을 활용하면 동작하는 데모를 빠르게 구현하고 고객의 피드백도 바로 반영할 수 있었습니다.   
또한 확정된 데모의 레이아웃과 컴포넌트를 실제 서비스 구현의 기반으로 활용할 수 있어, 시안에서 구현으로 전환하는 데 필요한 공수도 줄일 수 있었습니다.   

이러한 이유로 별도의 Figma 시안을 제작하는 대신, **데모 페이지를 구현해 개발 서버에 배포했습니다.**

<br/>

## **코드 기반 데모의 활용과 한계**

---

### **데모 페이지를 통한 요구사항 협의**

고객으로부터 요구사항을 전달받으면 핵심 기능과 사용 흐름을 확인할 수 있는 데모 페이지를 구현했습니다.   
처음부터 디자인의 완성도를 높이기보다는, 고객이 직접 화면을 조작하며 기능의 동작을 확인할 수 있도록 하는 데 집중했습니다.   

구현한 데모는 개발 서버에 배포한 뒤 고객과 함께 확인했습니다. 이후 피드백을 반영하고 변경된 화면을 다시 검토했습니다.   
이러한 방식으로 **요구사항 전달 → 데모 구현 및 배포 → 고객 확인 → 피드백 반영**의 과정을 반복했습니다.   
실제 동작을 기준으로 협의하면서 어떤 기능이 필요한지, 화면을 어떻게 구성할지와 같은 모호한 요구사항을 점차 구체화할 수 있었습니다.   

이러한 반복적인 협의는 고객과 개발자가 요구사항에 대한 이해를 맞추는 데 효과적이었으며, 이후에도 유지해야 할 중요한 과정이었습니다.

### **코드 기반 데모 방식의 한계**

코드 기반 데모는 요구사항을 구체화하는 데 효과적이었습니다. 다만 UI 시안을 서비스 코드로 직접 구현하고 공유 개발 서버를 통해 확인하는 방식에는 다음과 같은 한계가 있었습니다.

- **채택되지 않은 시안 코드의 낮은 활용도**   
  디자인이나 레이아웃을 제안할 때 고객이 여러 방향을 비교할 수 있도록 주로 2~3가지 시안을 준비했습니다.   
  각 시안의 레이아웃과 컴포넌트를 실제 코드로 구현했기 때문에, 방향이 확정되기 전부터 시안마다 구현 공수가 필요했습니다.   
  최종적으로 선택된 데모는 실제 서비스 구현의 기반으로 활용할 수 있었지만, 채택되지 않은 화면과 컴포넌트는 협의가 끝난 뒤 정리해야 했습니다.   

- **공유 개발 서버에 의존하는 데모 환경**   
  개발 서버는 여러 개발자가 기능을 배포하고 테스트하는 공유 환경이었습니다.   
  실제로 고객에게 데모 화면을 보여주는 도중 개발 서버가 중단되어 페이지에 접속하지 못한 경험도 있었습니다.   
  데모가 정상적으로 구현되어 있어도 개발 서버의 상태에 따라 시연과 요구사항 협의가 중단될 수 있었습니다.

- **화면 간 UI 일관성 관리의 어려움**   
  고객의 피드백을 빠르게 반영하기 위해 데모 페이지와 컴포넌트를 그때그때 수정하거나 추가했습니다.   
  프로젝트마다 필요한 화면을 개별적으로 구현하다 보니 새 화면과 기존 화면을 충분히 비교하고 화면 구성과 데이터 표현 방식의 일관성을 관리하기 어려웠습니다.
  그 결과 비슷한 성격의 데이터가 화면마다 서로 다른 형태로 표현됐고, 이러한 차이가 실제 서비스에도 이어졌습니다.

이러한 한계를 줄이기 위해서는 서비스 코드와 개발 서버에 의존하지 않고 다양한 UI를 탐색할 수 있는 방법이 필요했습니다.   
동시에 화면을 일관되게 구성할 수 있는 공통 기준도 필요했습니다.

## **Open Design과 AI 도구 도입**

---

### **Open Design을 도입한 이유**
이러한 문제를 해결할 방법을 고민하던 중, 팀원 한 분이 **`Open Design`**을 공유해 주었습니다.   
처음 접하는 도구였기 때문에 기능과 사용 방법을 살펴보고 간단한 UI를 직접 만들어 보며, 기존 요구사항 협의 과정에 적용할 수 있을지 검토했습니다.

> [Open Design](https://open-design.ai/)은 AI를 기반으로 UI 디자인 시안을 만들고 수정할 수 있는 오픈소스 디자인 도구입니다.
> <img src="/assets/img/post/frontend/ui-frontend-process/open-design-capture.png" alt="오픈 디자인 화면" style="display: block; max-width: 100%; height: auto; margin: 0 auto;">

Open Design을 직접 사용해 보면서, 다음과 같은 점에서 기존 데모 페이지 방식의 한계를 보완할 수 있을 것이라고 판단했습니다.   

- **직접 코드를 작성하지 않고 다양한 UI 시안 탐색**   
  화면의 목적과 필요한 기능을 자연어로 설명하면 여러 디자인 시안을 빠르게 생성하고 비교할 수 있었습니다.

- **개발 서버에 의존하지 않는 결과물 공유**   
  생성된 디자인을 HTML 파일로 내보낼 수 있어 별도의 데모 페이지를 개발 서버에 배포하지 않고도 결과물을 공유할 수 있었습니다.   
  개발 서버의 상태와 관계없이 디자인 시안을 확인할 수 있다는 점도 기존 방식의 한계를 보완할 수 있었습니다.

이러한 특징을 활용하면 **반복적인 코드 작성과 개발 서버에 대한 의존은 줄이면서도, 실제 화면을 함께 확인하며 요구사항을 구체화하는 기존 방식의 장점은 유지할 수 있을 것이라고 판단했습니다.**

### **Open Design 도입 이후 변화**

Open Design을 도입하면서 가장 크게 달라진 점은 **UI 시안을 탐색하는 단계와 실제 코드를 구현하는 단계를 분리할 수 있게 된 것이었습니다.**    

기존에는 여러 디자인 방향을 비교하기 위해 각 시안을 직접 코드로 구현해야 했습니다.   
실제로 고객이 세 가지 방향을 비교할 수 있도록 각 시안을 모두 코드로 구현했기 때문에, 방향이 확정되지 않은 초기 단계부터 구현 작업이 필요했고 최종적으로 선택되지 않은 시안의 코드도 함께 작성되었습니다.

Open Design을 활용한 이후에는 먼저 세 가지 UI 시안을 생성해 비교하고, 고객과 화면을 확인하며 방향을 구체화했습니다.
이후 시안이 확정되면 **선택된 한 가지 시안만 실제 서비스 코드로 구현했습니다.**

**<span style="background-color:yellow">그 결과 시안 비교에 필요한 선택지는 유지하면서도, 확정되지 않은 시안을 구현하고 정리하는 작업을 줄여 실제 개발에서는 확정된 UI 구현에 집중할 수 있게 되었습니다.</span>**

## **Open Design 템플릿과 팀 디자인 시스템 구축**

---

### **Open Design을 사용하면서 생긴 문제**

개발자뿐만 아니라 **팀 내 다른 구성원들도 서비스 기획 단계에서 Open Design을 활용하기 시작했습니다.**   

하지만 활용 범위가 넓어지면서 새로운 문제가 생겼습니다.   
각자가 필요한 화면을 개별적으로 생성하다 보니 화면마다 사용하는 색상이나 컴포넌트, 레이아웃이 달랐고, 기존 서비스의 UI와도 차이가 발생했습니다.   

그 결과 기획 단계에서 만들어진 화면을 실제 서비스에 반영하려면, 프론트엔드 개발자가 기존 서비스의 스타일과 구조에 맞게 다시 구현해야 했습니다.   
**요구사항을 화면으로 구체화하는 과정은 빨라졌지만, 생성된 UI와 실제 서비스 사이의 간극은 여전히 남아 있었습니다.**   

이를 줄이기 위해서는 <span style="background-color:yellow">**팀 내 누가 Open Design을 사용하더라도 기존 서비스의 UI를 기준으로 화면을 만들 수 있는 공통된 UI 기준이 필요했습니다.**</span>   

### **서비스의 UI 기준을 Open Design에 적용하기**

먼저 기존 서비스에서 사용하고 있는 CSS와 공통 컴포넌트, 화면 구성 방식을 바탕으로 반복적으로 사용되는 UI 규칙을 정리했습니다.   
여기에 프론트엔드 개발 규약을 함께 반영하여 Open Design에서 활용할 수 있는 `tokens.css`와 `DESIGN.md`를 구성했습니다.

#### **1. Design System으로 공통 UI 기준 정의하기**

Open Design의 Design System은 **AI가 화면을 생성할 때 참고할 디자인 기준을 정의하는 기능**입니다.   
제가 구성한 Design System에서는 주로 다음 항목을 활용했습니다.   

- **`tokens.css`**   
  Brand Color, Background Color, Text Color 등 색상뿐만 아니라 Typography, Spacing, Border Radius 등 반복적으로 사용하는 디자인 값을 정의   
- **`DESIGN.md`**   
  디자인 원칙과 레이아웃, 컴포넌트 등 서비스 전반의 디자인 기준을 정의

이를 통해 사용자가 매번 프롬프트에 서비스의 색상이나 버튼 스타일, 화면 구성 규칙을 반복해서 설명하지 않아도 **동일한 기준을 참고해 UI를 생성할 수 있도록 했습니다.**

#### **2. 반복되는 화면 구조를 Template으로 구성하기**

또한 대시보드 페이지처럼 **반복적으로 사용하는 화면 구조는 HTML Template으로 구성했습니다.**   
Design System이 화면을 어떻게 표현할 것인지에 대한 공통 기준을 제공한다면, Template은 새로운 디자인 시안의 출발점 역할을 합니다.   
이를 통해 새로운 화면을 만들 때마다 빈 화면에서 시작하지 않고, 기존 서비스의 기본 구조를 바탕으로 필요한 기능과 화면을 구체화할 수 있도록 했습니다.

#### **3. 팀의 공통 UI 환경으로 확장하기**
